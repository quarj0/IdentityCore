# Compatible deployment and rollback

Use a rehearsal restored from a recent encrypted backup. Initial schema installation on an empty database is a maintenance/bootstrap operation, not a rolling deployment. Rolling deployments start with the previous release's schema already applied.

1. Inspect the migration plan and run `manage.py check_rollout_migrations` against the candidate and current database. Unsafe, destructive or ambiguous operations block promotion. An ordinary Python field default does not protect old code: its database default is removed after migration. Use unindexed nullable expansion or a non-null scalar server default, and do not add uniqueness/primary-key changes in the same release. Indexed fields and relationships need a separate staged design; build indexes concurrently in a non-atomic migration. NULL/expression server defaults do not establish automatic compatibility. Data migration, rename and contraction require a separately designed staged release.
2. Run `manage.py migrate_for_rollout`. The command rechecks compatibility, uses a three-second PostgreSQL lock timeout, applies only the accepted expansion, and restores the previous lock timeout. A failure blocks rollout. Investigate any invalid concurrently built index before retrying; do not automatically reverse committed schema.
3. Start the candidate processes with consumers initially stopped or an instance-local drain marker present. Verify dependency readiness before resuming. Each instance uses an absolute `DEPLOYMENT_DRAIN_FILE` path, default `/tmp/identitycore-draining`. API and worker containers drained together must share this marker; isolated instances need separate commands/markers.
4. Drain each old instance with `manage.py deployment_drain --worker celery@INSTANCE --timeout 60`. Readiness becomes 503 before the command cancels only that worker's consumers. It waits for two consecutive empty active/reserved/scheduled snapshots; any intervening work resets the confirmation. A missing reply, unsupported queue or timeout blocks rollout and leaves the marker in place. Never revoke/terminate in-flight tasks to make the gate pass. A scheduled future task may require extending the maintenance plan instead of forcing replacement.
5. Stop a successfully drained worker with graceful SIGTERM. Keep the old expanded schema and durable processing rows. Start replacement consumers, run `manage.py deployment_drain --resume` on a healthy replacement instance, then gate traffic on HTTPS `/api/v1/ready` and the deployed security workflow. The drain command's resume action removes the marker only after database/broker checks succeed; it does not restart consumers. The operator must start them before routing traffic.
6. Increase traffic only after both deployment gates pass. Preserve sanitized evidence. Liveness `/api/v1/health` is deliberately separate from readiness and cannot authorize promotion.

The readiness endpoint reports only `ready`/`unavailable`, uses no-store caching, checks database connectivity and the Redis broker with bounded waits, and returns 503 while draining. It exposes no DSN, exception or dependency names. New document/biometric processing generations are not acquired on a draining instance. Already acquired work retains its generation and may complete normally. One-message prefetch reduces stranded reservations. Late acknowledgement and requeue-on-worker-loss apply only to document/biometric tasks with durable job ownership, and existing durable job ownership/outcome checks govern duplicate processing. Notification and other side-effect tasks keep their existing acknowledgement behavior.

Rollback changes application code and restarts healthy consumers **without** down migrations, clearing processing leases, deleting committed provider results or changing evidence. The previous code must still write/read the expanded schema. Wait for old generations to finish, or let the existing stale-lease recovery sweep recover worker loss after its lease expires. Do not shorten live leases to force progress. Broker publication and provider-result recovery must preserve the recovery marker and avoid repeating committed provider calls. Contract and remove old columns only in a later release after old binaries and queued payload versions have been retired.

Run the readiness gate against each candidate's externally routable HTTPS origin:

```sh
python scripts/check_deployment_health.py --api https://api.candidate.example.org --output readiness-report.json
```

It checks fresh status/no-store payloads, validates certificate trust/TLS 1.2+, refuses redirects, and exits nonzero if readiness cannot be established. Timeout is bounded to 120 seconds. Proxy and CA settings remain verified; owned private CAs may use `--ca-file` locally. Promotion automation must depend on successful readiness and security jobs. Neither fixture tests nor liveness substitute for a fresh deployed report.

Validation includes worker-target isolation, missing replies, timeout preserving in-flight work, resume health checks, blocked acquisition with preserved active completion, conservative migration classification, and a real PostgreSQL old/new model overlap fixture. The PostgreSQL fixture expands a nullable field, verifies writes from both versions, then verifies code rollback preserves data written by the new version.

The isolated load harness explicitly keeps Gunicorn connections alive for two seconds and retires idle client connections after one second. This avoids reusing sockets after the server's idle lifetime. Connection resets and failed requests still fail the journey and promotion gate; no request retry or success threshold is relaxed. Both lifetimes are retained in the sanitized load report.
